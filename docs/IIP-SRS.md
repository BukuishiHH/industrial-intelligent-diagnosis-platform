## 1. 项目概述

### 1.1 项目背景

设备故障诊断是工业运维的核心环节。当前一线团队主要依赖人工排查与资深工程师经验判断，面临三类突出问题：

1. **排查耗时长**：故障发生后需人工翻阅大量设备手册、检修规程、历史工单，逐项比对现象，平均定位周期长。
2. **经验依赖度高**：诊断结论高度依赖少数资深工程师，人员流动或夜班/异地场景下响应能力骤降。
3. **知识传承困难**：隐性的诊断经验难以标准化沉淀，新人成长周期长，历史案例复用率低。

与此同时，工业现场已积累了大量可用数据资产：**27 份工业文档（合计 1109 页、切分为 5091 个向量块）**与**4 台设备共 24 个传感器**的实时/历史运行数据。这些数据为"以 AI 辅助甚至主导故障诊断"提供了基础。

为此，本项目拟建设**工业智能诊断平台（IIP）**：以工业文档知识库为知识底座，以传感器时序数据为事实依据，采用 **LangGraph 单图统一编排**串联诊断流程，并引入 **A2A（Agent-to-Agent）+ MCP（Model Context Protocol）双协议分层架构**实现能力解耦与工具标准化接入，最终把 AI 诊断从"演示可用"推进到"**生产可用**"级别。

### 1.2 项目目标

| 编号 | 目标 | 衡量指标（建议） |
| --- | --- | --- |
| G1 | 构建可检索、可溯源的工业文档知识库 | 27 份文档、1109 页完成解析入库，形成 5091+ 向量块；检索结果 100% 可溯源到原文页码 |
| G2 | 打通设备传感器数据链路 | 接入 4 台设备、24 个传感器，数据完整率 ≥ 99%，支持实时与历史数据查询 |
| G3 | 实现 AI 自动故障诊断 | 常见故障类型诊断准确率 ≥ 85%，端到端诊断响应 P95 ≤ 60s，输出含置信度与证据链 |
| G4 | 沉淀与传承诊断知识 | 每次诊断过程与人工确认结果自动沉淀为案例，形成可持续迭代的知识闭环 |
| G5 | 提供服务化、可扩展的架构 | 基于 LangGraph 单图编排 + A2A/MCP 双协议分层，新增设备/工具/Agent 以插件方式接入，不改动核心编排 |
| G6 | 达到生产可用标准 | 可用性 ≥ 99.5%，具备权限、审计、降级、可观测能力，通过生产可用性验收 |

### 1.3 项目范围

**范围内（In Scope）：**

- 工业文档知识库模块：文档接入、解析、切块、向量化、混合检索、溯源。
- 传感器数据处理模块：数据接入、清洗、对齐、特征提取、异常检测。
- AI 诊断 Agent 模块：基于 LangGraph 的多步诊断推理与工具调用。
- A2A + MCP 双协议分层调度模块：协议适配、服务注册发现、分层路由与编排。
- 诊断结果输出模块：诊断报告生成、多形态输出、人机协同反馈。
- 支撑能力：权限、审计、配置管理、可观测与运维。

**范围外（Out of Scope，本期不实现）：**

- 设备自动化控制与远程反向操作（仅诊断，不执行控制指令）。
- 传感器硬件选型、现场布线与网关施工。
- 备件库存与采购系统对接（仅预留接口）。
- 面向消费者端的移动 App（（假设）本期以 Web 与开放 API 为主）。

## 2. 业务需求

### 2.1 业务痛点

| 编号 | 痛点 | 现状表现 | 平台应对 |
| --- | --- | --- | --- |
| BP-01 | 人工排查耗时长 | 故障定位需跨多份文档与历史工单人工比照，响应以小时/天计 | 知识库秒级检索 + AI 多步诊断，端到端分钟级给出结论 |
| BP-02 | 经验依赖度高 | 结论质量取决于个人经验，夜班/异地响应能力不足 | 将诊断 SOP 与专家经验结构化为 Agent 推理链与故障库 |
| BP-03 | 知识传承困难 | 经验留存于个人，新人成长慢，案例复用率低 | 诊断过程全量留痕并沉淀为可检索案例，形成组织知识资产 |
| BP-04 | 数据与知识割裂 | 文档知识、传感器数据、历史工单分散在不同系统 | 以统一编排将知识检索与数据分析融合为一条诊断链 |
| BP-05 | 结论缺乏可解释性 | 人工结论难以复现与复核，责任边界模糊 | 输出证据链、引用来源、置信度与推理过程 |
| BP-06 | 工具集成成本高 | 各数据源/工具接口异构，难以快速扩展 | MCP 标准化工具接入 + A2A 解耦 Agent 协作 |

### 2.2 业务场景

**场景一：实时异常诊断（在线监测告警驱动）**

某设备传感器触发异常告警 → 平台自动拉取该设备近期时序数据 → 结合异常特征在知识库检索对应故障模式与处置规程 → AI 诊断 Agent 多步推理并给出根因假设与置信度 → 生成诊断报告并推送值班工程师。

**场景二：人工问诊式诊断（工程师主动发起）**

工程师以自然语言描述现象（如"3 号设备振动升高伴随温度异常"）→ 平台澄清关键信息（设备、时间窗、工况）→ 调取数据与文档证据 → 输出候选故障排序与处置建议。

**场景三：知识查询与规程问答**

工程师查询某设备某部件的检修标准、报警阈值或处置步骤 → 知识库检索并给出**带原文页码引用**的答案，避免大模型幻觉。

**场景四：诊断结果复核与知识回流**

工程师确认/修正 AI 诊断结论 → 平台记录反馈 → 高质量结论沉淀为案例与故障库条目 → 用于后续检索与提示词/模型优化。

**场景五：趋势预测与预防性维护（（假设）为二期增强，本期可做试点）**

基于历史时序数据识别劣化趋势 → 提前预警并给出维护建议窗口。

## 3. 功能性需求

### 3.1 工业文档知识库模块

| 编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| FR-01-01 | 支持批量导入工业文档，兼容 PDF（含扫描件）、Word、Excel、图片、文本等格式；本期首批导入 27 份文档、共约 1109 页 | M |
| FR-01-02 | 对扫描件与图片执行 OCR 识别，识别结果支持人工校正；OCR 后文本可参与检索 | M |
| FR-01-03 | 对文档执行结构化解析：识别章节、标题、表格、图注、参数阈值、检修步骤等语义单元 | M |
| FR-01-04 | 按语义/结构进行智能切块，生成向量块（本期基线为 5091 块），切块支持重叠与元数据标注（文档、页码、章节、设备型号） | M |
| FR-01-05 | 对文本块生成向量并建立索引，支持向量检索、关键词检索及二者融合的混合检索，并可叠加重排序（Rerank） | M |
| FR-01-06 | 检索结果必须携带**原文出处**（文档名、页码、段落片段），实现 100% 可溯源 | M |
| FR-01-07 | 支持文档版本管理与增量更新：文档新增/修订后可增量重建对应向量块，不破坏历史引用 | S |
| FR-01-08 | 提供知识库管理界面：上传、分类、检索预览、失效/停用、权限设置 | S |
| FR-01-09 | （假设）构建轻量知识图谱，关联"设备—部件—故障现象—故障原因—处置措施"，支撑推理链路扩展 | C |
| FR-01-10 | 支持知识库健康度监测：覆盖率、检索命中率、无答案问题统计 | C |

**输入**：工业文档原始文件、文档元数据。
**输出**：结构化文本、向量块、检索结果（含来源引用）。
**关键验收点**：27 份文档全部成功入库无丢失；随机抽取查询返回结果可定位到正确原文页码。

| FR-02-06 | 异常检测：基于阈值规则与（（假设）无监督/统计/轻量模型）方法识别异常并生成告警事件 | M |

**关键验收点**：24 个传感器全部接入并稳定上报；给定时间窗可正确返回数据与特征。

### 3.4 A2A + MCP 双协议分层调度模块

> 定位：这是本平台"生产可用"的关键架构支撑。**LangGraph 单图统一编排**负责流程与状态，**MCP** 负责标准化能力/工具接入，**A2A** 负责 Agent 之间与跨系统的协作通信。

| 编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| FR-04-01 | 基于 **LangGraph 构建单一统一编排图**（统一 State、节点=能力步骤、边=条件路由），作为诊断流程的唯一编排入口 | M |
| FR-04-02 | 图节点支持封装"Agent 调用""工具调用""数据查询""人工确认"等动作，并支持条件分支、循环与中断/恢复 | M |
| FR-04-03 | 实现 **MCP 协议层**：以 MCP Server 方式标准化封装工具与数据源（知识检索、时序查询、设备台账、报告生成等），以 MCP Client 统一调用 | M |
| FR-04-04 | MCP 工具需声明能力描述、入参/出参 Schema、权限与超时；新增工具不改动编排代码即可接入 | M |
| FR-04-05 | 实现 **A2A 协议层**：支持 Agent 注册、发现、能力声明、任务下发与结果回传 | M |
| FR-04-06 | 支持至少以下 Agent 角色（（假设））：诊断 Agent、知识检索 Agent、数据分析 Agent、报告 Agent；各角色可独立部署与横向扩展 | M |
| FR-04-07 | 分层调度：编排层按任务类型路由到相应协议层与能力节点，协议层屏蔽底层实现差异 | M |
| FR-04-08 | 统一任务上下文传递：跨 Agent/工具调用共享设备、时间窗、证据等上下文，避免信息丢失 | M |
| FR-04-09 | 调度可靠性：支持超时、重试、幂等、熔断、降级与失败兜底 | M |
| FR-04-10 | 全链路可观测：记录每次调用链路、耗时、输入输出摘要，支持问题定位 | S |
| FR-04-11 | （假设）协议版本兼容与灰度：MCP/A2A 服务支持多版本共存与灰度切换 | C |

**输入**：诊断任务、各 Agent/工具能力注册信息。
**输出**：统一编排执行结果、跨 Agent 协作结果。
**关键验收点**：新增一个 MCP 工具可零改动接入并在诊断中被调用；A2A 跨 Agent 任务可正确下发与回传。

## 6. 系统架构需求

### 6.1 架构原则

1. **单图统一编排**：以 LangGraph 单一编排图为唯一流程入口，避免多图/多流程割裂，统一状态与上下文。
2. **协议分层解耦**：MCP 负责"能力/工具"标准化接入，A2A 负责"Agent 协作"通信，编排层与实现层解耦。
3. **知识与数据双驱动**：文档知识提供"应然"依据，传感器数据提供"实然"证据，二者在诊断链中融合。
4. **可解释与可溯源**：任何结论必须可回溯到证据，AI 输出定位为辅助建议。
5. **生产可用优先**：从一开始即考虑可用性、可靠性、安全性与可观测性，而非事后补丁。
6. **可扩展与可替换**：组件接口化、能力插件化，支持能力与模型替换升级。

### 6.2 分层架构（自顶向下）

| 层次 | 职责 | 关键内容 |
| --- | --- | --- |
| 接入层 | 用户与系统交互 | Web 控制台、开放 API、消息推送、第三方系统对接 |
| 应用编排层 | 流程与状态编排 | **LangGraph 单图统一编排**、统一 State、条件路由、检查点 |
| 协议适配层 | 标准化接入与协作 | **MCP 协议层**（工具/数据接入）+ **A2A 协议层**（Agent 协作） |
| 能力服务层 | 提供具体能力 | 诊断 Agent、检索 Agent、数据分析 Agent、报告 Agent、MCP 工具集 |
| 数据与知识层 | 数据与知识存储 | 文档知识库、向量库、知识图谱、时序库、案例库、台账 |
| 基础设施层 | 运行与支撑 | 容器编排、消息队列、缓存、监控告警、日志、密钥管理 |

### 6.3 关键技术需求

| 编号 | 需求描述 |
| --- | --- |
| AR-01 | 编排引擎采用 LangGraph，支持图定义、状态管理、条件边、循环、人工中断（Human-in-the-loop）与检查点恢复 |
| AR-02 | MCP 层提供 Server 与 Client 能力，统一工具注册、Schema 校验、鉴权与调用审计 |
| AR-03 | A2A 层提供 Agent 注册发现、能力协商、任务生命周期管理（下发/进度/结果/取消） |
| AR-04 | 检索采用"向量 + 关键词 + Rerank"混合方案，返回带来源的结果 |
| AR-05 | 时序数据采用专业时序库存储，支持高写入与窗口查询 |
| AR-06 | 全链路可观测：调用链追踪、指标（延迟/成功率/成本）、日志与告警 |
| AR-07 | 部署支持容器化与水平扩展，支持私有化部署与网络隔离 |
| AR-08 | 统一配置管理：设备台账、传感器参数、模型参数、提示词模板、协议配置均可配置化管理 |

### 6.4 核心诊断流程（示例）

```
[任务接入] → [意图识别/信息澄清] → [知识检索(MCP)] ┐
                                   [数据查询(MCP)] ┼→ [证据聚合] → [假设生成]
                                                                     ↓
[报告输出] ← [人工确认] ← [结论生成/置信度评估] ← [假设验证(A2A 协作/工具调用)]
                                     ↑___________________________|
                                  （证据不足则回到检索/澄清）
```

> 该流程由 LangGraph 单图承载；图中各能力节点通过 MCP 调用工具/数据，需要多 Agent 协同时通过 A2A 下发子任务。
