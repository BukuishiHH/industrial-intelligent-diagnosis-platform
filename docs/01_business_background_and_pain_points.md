## 1. 业务背景

### 1.1 行业背景

工业设备运维正在从“事后维修、定期检修”向“状态检修、预测性维护、智能诊断”演进。随着设备复杂度提升、产线连续性要求提高、熟练工程师数量不足，传统人工排查模式的瓶颈越来越明显。工业现场同时积累了可观的数字化资产，包括设备手册、检修规程、故障案例、工艺标准等文档，以及振动、温度、压力、电流、转速等传感器时序数据。

本项目面向工业设备故障诊断场景，利用工业文档知识和设备传感器数据，构建 AI 驱动的诊断平台，帮助一线工程师缩短故障定位时间、降低经验依赖、沉淀组织知识，并将 AI 诊断能力推进到生产可用级别。

### 1.2 现状与矛盾

| 现状 | 具体表现 | 业务后果 |
| --- | --- | --- |
| 文档知识分散 | 27 份工业文档、约 1109 页内容分散在手册、规程、案例、图纸中 | 查阅慢、易遗漏、版本不一致 |
| 数据与知识割裂 | 传感器数据与文档知识分属不同系统，未形成联合证据链 | 难以“以数据验证知识、以知识解释数据” |
| 诊断依赖个人经验 | 复杂故障依赖少数资深工程师判断 | 夜班/异地/人员流动时响应能力下降 |
| 知识传承困难 | 诊断经验停留在个人头脑或零散记录中 | 新人成长慢、案例复用率低、组织能力难沉淀 |
| 结论可解释性不足 | 人工判断过程难以复现、难以审计 | 责任边界模糊，AI 结论难以被信任 |
| 工具集成成本高 | 数据源、算法、报告工具接口异构 | 新能力接入慢，平台扩展困难 |

### 1.3 项目输入资产

- **知识资产**：27 份工业文档，约 1109 页；按推荐切块策略形成约 5091 个向量块。
- **数据资产**：4 台设备、24 个传感器，覆盖实时流数据与历史数据。
- **业务诉求**：解决人工排查耗时长、经验依赖度高、知识传承困难等痛点。
- **架构约束**：采用 LangGraph 单图统一编排，引入 A2A + MCP 双协议分层架构。
- **目标定位**：AI 诊断达到生产可用标准，具备可解释、可追溯、可扩展、可持续运营能力。

## 2. 核心痛点分析

### 2.1 痛点一：人工排查耗时长

**现状**：设备报警或异常发生后，工程师需要：

1. 在现场确认现象并记录工况；
2. 翻阅设备手册、检修规程、历史工单；
3. 调取传感器数据，判断异常时间段和特征；
4. 结合经验提出候选故障并逐项排查；
5. 编写诊断记录和处置建议。

**问题根因**：

- 文档检索依靠人工翻页和关键词搜索，缺少语义检索与结构化定位；
- 传感器数据查询工具分散，缺少统一的时间窗查询与特征提取能力；
- 诊断步骤没有标准化编排，信息在多个系统间反复复制。

**平台应对**：

- 文档知识库支持语义检索、混合检索和原文页码溯源；
- 传感器数据服务支持按设备、传感器、时间窗统一查询与特征计算；
- LangGraph 单图编排串联“意图识别—检索—取数—假设—验证—报告”全过程。

**建议指标**：

| 指标 | 现状基线（假设） | 目标值 |
| --- | --- | --- |
| 常规故障定位时间 | 60～240 分钟 | P95 ≤ 10 分钟（平台辅助定位） |
| 端到端诊断报告生成 | 不适用 | P95 ≤ 60 秒（不含人工确认） |
| 知识检索耗时 | 5～30 分钟人工翻阅 | P95 ≤ 1.5 秒 |

### 2.2 痛点二：经验依赖度高

**现状**：

- 诊断质量取决于少部分资深工程师；
- 故障模式、处置经验、阈值判断标准大多以隐性知识存在；
- 夜班、节假日、异地支援时，专家资源无法及时到位；
- 新员工需要长期跟师学习，独立诊断能力形成慢。

**平台应对**：

- 将诊断 SOP、故障模式、判断规则结构化为诊断策略；
- 通过 RAG 检索文档知识和历史案例，降低对个人记忆的依赖；
- 使用“假设—验证”多步推理，将专家诊断思路显性化、标准化；
- 当证据不足时主动澄清或转人工，避免无依据判断。

**建议指标**：

| 指标 | 目标值 |
| --- | --- |
| 典型故障诊断准确率 | ≥ 85%（基于约定测试集） |
| 证据链完整率 | ≥ 95% 结论包含可追溯证据 |
| 无依据拒答/转人工率 | 证据不足场景 100% 明确提示 |
| 初级工程师独立处理率 | 较现状提升 ≥ 30%（试点评估） |

### 2.3 痛点三：知识传承困难

**现状**：

- 故障处理过程缺少结构化记录，历史案例难以复用；
- 专家离职或调岗后，经验随人流失；
- 文档更新后，旧知识未被标记失效，导致误用；
- 诊断结论未形成可检索、可评价、可迭代的知识闭环。

**平台应对**：

- 每次诊断自动生成结构化记录，包含现象、证据、假设、结论、置信度和处置建议；
- 人工复核结果回流为案例库和故障库条目；
- 文档版本化、增量入库、失效管理，保证引用知识是最新有效版本；
- 通过统计与复盘驱动知识库持续优化。

**建议指标**：

| 指标 | 目标值 |
| --- | --- |
| 诊断过程留痕率 | 100% |
| 案例回流率 | 人工确认/修正结论 100% 可沉淀 |
| 知识库引用可溯源率 | 100% |
| 新人上手周期 | 较传统模式缩短 ≥ 40%（试点评估） |

### 2.4 痛点四：数据与知识割裂

**现状**：知识库、传感器时序库、设备台账、历史工单、报告系统相互独立，缺少统一上下文。诊断时需要人工在系统间搬运信息，容易造成数据不一致和证据缺失。

**平台应对**：

- 建立统一设备台账和传感器元数据；
- 以诊断任务上下文（设备、时间窗、现象、工况）贯穿全流程；
- 通过 MCP 工具层标准化封装知识检索、时序查询、特征计算、报告生成等能力；
- 在诊断结论中同时引用文档证据和数据证据。

### 2.5 痛点五：结论缺乏可解释性

**现状**：人工诊断结论难以复现；AI 大模型存在幻觉风险。若只给出一个“疑似故障”结论，用户无法判断可信度，也不敢用于生产决策。

**平台应对**：

- 每条结论必须附带证据链：文档名称 + 页码 + 原文片段；传感器 + 时间窗 + 特征值；
- 输出置信度等级和不确定性说明；
- 建立证据充分性校验和拒答机制；
- 保留完整推理轨迹，支持审计与复盘；
- 定位为“AI 辅助建议、人工最终确认”。

### 2.6 痛点六：工具集成与扩展困难

**现状**：每新增一种数据源或算法工具，都需要修改主流程代码，导致平台演进缓慢、回归风险高。

**平台应对**：

- 用 MCP 统一工具注册、Schema 校验、权限与调用审计；
- 用 A2A 统一 Agent 注册、发现、任务下发与结果回传；
- LangGraph 编排图只依赖稳定接口，不依赖具体实现；
- 新增设备、文档、工具、Agent 均以插件化方式接入。

## 3. 业务目标与价值

### 3.1 业务目标

| 编号 | 目标 | 衡量指标（建议） |
| --- | --- | --- |
| BG-01 | 构建可检索、可溯源的工业文档知识库 | 27 份文档、约 1109 页完成入库，形成 ≥ 5091 向量块；检索结果 100% 可溯源 |
| BG-02 | 打通设备传感器数据链路 | 4 台设备、24 个传感器稳定接入；数据完整率 ≥ 99% |
| BG-03 | 实现 AI 自动故障诊断 | 典型故障诊断准确率 ≥ 85%；端到端诊断 P95 ≤ 60s；输出含证据链与置信度 |
| BG-04 | 沉淀与传承诊断知识 | 诊断过程全量留痕；人工确认结果自动沉淀为案例 |
| BG-05 | 构建可扩展的生产级架构 | LangGraph 单图编排 + A2A/MCP 双协议分层；新增能力插件化接入 |
| BG-06 | 达到生产可用标准 | 可用性 ≥ 99.5%；具备权限、审计、降级、可观测、成本控制能力 |

### 3.2 业务价值

**对一线工程师**：

- 减少跨系统查找和手工比对；
- 快速获得候选故障排序、证据链和处置建议；
- 降低对个人记忆和经验的依赖。

**对运维团队**：

- 缩短 MTTR，提高设备可用率和产线连续性；
- 将专家经验转化为可复用的组织资产；
- 通过数据与知识融合提升诊断一致性。

**对企业**：

- 降低因非计划停机造成的损失；
- 提升知识传承效率和新人培养速度；
- 为预测性维护、智能运维奠定数据与平台基础。

## 5. 项目范围

### 5.1 范围内（In Scope）

- 工业文档知识库：接入、解析、OCR、切块、向量化、混合检索、原文溯源、版本管理。
- 传感器数据处理：接入、清洗、对齐、特征提取、异常检测、统一数据服务。
- AI 诊断 Agent：任务理解、信息澄清、多步推理、工具调用、置信度评估、报告生成。
- 双协议分层：LangGraph 单图编排、MCP 工具层、A2A 协作层。
- 诊断输出：结构化报告、多形态推送、人工复核、案例回流。
- 平台支撑：认证授权、审计、配置管理、可观测、告警、成本控制。

### 5.2 范围外（Out of Scope）

- 设备自动控制与远程反向操作（平台只诊断，不执行控制指令）。
- 传感器硬件选型、现场布线与网关施工。
- 备件库存与采购系统的深度对接（仅预留接口）。
- 面向公众的移动 App（本期以 Web 与开放 API 为主）。
- 预测性维护高级能力（作为二期增强，本期可做试点）。

## 6. 关键假设与约束

### 6.1 关键假设

1. 27 份工业文档可提供电子版或可扫描版本，解析质量可接受。
2. 4 台设备、24 个传感器具备稳定的数据采集链路，可提供实时或历史数据。
3. 现场网络支持平台与采集系统、业务系统之间的最小必要通信。
4. 业务方能够提供典型故障场景、诊断规则和专家复核资源。
5. 大语言模型可私有化部署或通过合规通道调用，满足数据安全要求。
6. 量化指标可在需求评审阶段确认并冻结。

### 6.2 约束条件

| 编号 | 约束 | 说明 |
| --- | --- | --- |
| C-01 | 数据规模约束 | 首批 27 份文档、约 1109 页、约 5091 向量块；4 台设备、24 个传感器 |
| C-02 | 架构约束 | 必须采用 LangGraph 单图统一编排，引入 A2A + MCP 双协议分层架构 |
| C-03 | 安全约束 | 支持私有化部署、权限控制、审计留痕与数据脱敏 |
| C-04 | 定位约束 | AI 仅提供辅助诊断建议，最终结论需人工确认 |
| C-05 | 合规约束 | 满足工业数据安全要求，必要时满足等级保护或行业规范 |
| C-06 | 资源约束 | 算力、模型、工期与预算需在启动阶段确定 |

## 8. 结论

本项目以“知识 + 数据 + 编排 + 协议”四位一体为思路，面向真实工业诊断场景解决效率、经验、传承、解释性和扩展性问题。项目成败不仅取决于模型效果，更取决于数据质量、知识治理、流程闭环和生产级工程能力。后续文档将围绕业务功能、智能体职责、总体架构、详细设计、测试验收等维度展开。
